# 1.5 — Trustworthy test runs and clean dependencies

Fragment for the 1.5 integrator. It holds everything README.md, docs/USER_GUIDE.md, docs/API.md, docs/LOGIC.md,
docs/DEPLOY.md and CHANGELOG.md need from this package; none of those files were edited here.

Findings fixed: CODE-7 (tests that depend on the real date), CLM-7, CODE-8 (CI part) and SECURITY-MISSED-4 (the tests
now run on Linux and Mac), CODE-4 and SEC-5 (known security problems in packages, and nothing checking for them).

---

## 1. What changed, in plain words

- **The tests no longer depend on today's date.** One test assumed 12 Nov 2026 was still in the future, and others
  broke at midnight, in January or when the business clock was moved. They now use a fixed business day or dates
  worked out from the clock they set. A new command, `npm run test:dates`, runs the whole suite as if it were
  another day, so this kind of problem shows up long before the calendar gets there.
- **Every change is checked on Linux and on a Mac.** The full checks (types, all the tests, the API smoke test, the
  build) now run on both, not only on Linux. The start/stop checks on both systems and three Node versions stay.
- **Known security problems in packages are checked automatically.** Every change, and every Monday, CI runs
  `npm audit`; a high or critical problem in a package the app runs with fails the check.
- **Package updates come in by themselves.** Dependabot opens grouped pull requests each Monday for the app's
  packages and for the CI actions, and security fixes as soon as they are published. CI checks each one on Linux and
  Mac before anyone merges it.
- **The four known package problems are fixed** (2 high, 2 moderate): body-parser, zod, and nodemailer (inside
  mailparser, used for statement emails). `npm audit` now reports none.
- **Clearer messages when a form is refused.** The server's own wording for a missing or wrong field is now plain:
  "Required", "Use at most 6 characters", "Choose one of: charity, energy, …", "Must be more than 0". A refused request
  lists at most 20 problems, then "And 12 more problems".

Nothing changes in how anyone uses the app, and there is nothing to upgrade in the database.

## 3. New command (developers)

| Command | What it does |
| --- | --- |
| `npm run test:dates` | Runs `npm test` once per date. With no dates it uses four awkward moments ahead of today: 23:45 on 31 Dec next year, a Sunday at 23:30 in early January, midnight starting a summer-time Monday, and a spring Wednesday on the business clock only. |
| `npm run test:dates -- 2027-06-01T09:30 2028-01-01` | The dates you name (UK local time unless you add `Z`). |
| `npm run test:dates -- business:2027-06-01T09:30` | Moves only the business clock (as `LM_BUSINESS_NOW` does) and leaves the computer's clock alone: finds a test that mixes the two clocks. |

How it moves the clock: `scripts/fake-now.mjs` is loaded with `NODE_OPTIONS=--import=…` and shifts `Date` (new
Date(), Date.now(), Date()) in every test process and in any server a test starts; the shifted clock keeps ticking.
Timers, `performance.now()`, file times and SQLite's own `'now'` stay real. Two environment variables are used by this
script only, never by the app: `LM_TEST_FAKE_NOW` (the date asked for) and `LM_TEST_CLOCK_OFFSET_MS` (worked out once
and passed to child processes so they share one clock).

No new settings or environment variables for the app itself.

## 5. Packages: before and after

`npm audit --omit=dev` before (1.4.0):

```
body-parser  2.0.0 - 2.3.0   Severity: high      GHSA-27r3-jxmh-p828 (denial of service, trailing bytes after a compressed body)
nodemailer  3.0.0 - 10.1.3   Severity: moderate  GHSA-8c8m-p3m8-cjg8, GHSA-m943-m63m-w62w, GHSA-85x2-q946-cp5h (addressparser)
  mailparser  2.3.1 - 3.9.42 (depends on nodemailer)
zod  <4.6.6                  Severity: high      GHSA-mrhx-c7xc-m3w5 (memory exhaustion, oversized constrained collections)
4 vulnerabilities (2 moderate, 2 high)
```

The full `npm audit` (development tools included) showed the same four.

After: `npm audit --omit=dev` → `found 0 vulnerabilities`; `npm audit` → `found 0 vulnerabilities`.

| Package | Before | After | How |
| --- | --- | --- | --- |
| body-parser (through express) | 2.3.0 | 2.4.0 | `npm audit fix`, lockfile only |
| mailparser (server) | 3.9.36 | 3.12.4 (exact pin kept) | brings nodemailer 10.0.14 → 10.2.1 |
| zod (server) | ^3.24.4 (3.25.76) | ^4.6.7 (4.6.7) | code moved to the zod 4 API |

What the zod problem meant here: zod 3 checked every item of a list before noticing the list was too long, and the
server's 400 answer listed every problem. 100,000 bad ids sent to a list capped at 200 came back as 100,001 problems:
a 6.6 MB answer to a 0.4 MB request. Every capped list in a request body behaved the same, including ones anyone
signed in can send (video watch progress).
On zod 4 the same request gets one problem ("At most 200") in under 30 ms. The `zod/v3` import that ships inside the
zod 4 package still has the old code, which is why the routes use the zod 4 API rather than that import.

The body-parser problem could not be made to misbehave here (Node 22.22 and 20.20): a gzip body with extra bytes
gets a clean 400, deflate and brotli bodies are read and answered. The update is still taken (it is a plain bug-fix
release), and a test sends all three with extra bytes and checks the server keeps answering.

## 6. API changes (docs/API.md)

- **Validation errors** keep their shape, `400 { "error": "Validation failed", "details": [{ "path", "message" }] }`,
  with two changes:
  - zod's own messages are plain words. Where a schema gives no message of its own: missing field "Required"; wrong
    type "Expected text" / "Expected a number" / "Expected a whole number" / "Expected true or false" / "Expected a
    list"; text too short or long "Use at least N characters" / "Use at most N characters" (an empty required text is
    "Required"); numbers "Must be N or more", "Must be more than N", "Must be N or less", "Must be less than N";
    lists "Add at least one", "Add at least N", "At most N"; a value not in the list "Choose one of: a, b, c" (up to 8
    choices, otherwise "Not one of the choices"); email "Enter a valid email address"; other formats "Not in the
    expected format"; unknown fields on strict bodies "Not expected here: x, y". A schema's own message (for example
    "Expected a hex colour like #4F46E5") is unchanged.
  - **At most 20 details.** When there are more, a 21st detail `{ "path": "", "message": "And N more problems" }`
    says how many were left out.
  - A list over its limit gives one detail for the list ("At most 200") and none for its items.
- **PATCH bodies change only the fields they send.** This was already the rule; it is now guaranteed by
  `parsePatch` (below) for `PATCH /users/:id`, `/campaigns/:id`, `/events/:id`, `/gauges/:id`,
  `/recruitment/candidates/:id`, `/recruitment/interviews/:id` and `/recruitment/questions/:id`.

## 8. For developers (docs/MAINTAINERS.md or the README's development section)

zod 4 rules for this codebase:

- **PATCH:** `const patch = parsePatch(schema, req.body)`, never `schema.partial().parse(req.body)`. zod 4 applies
  `.default()` inside optional fields, so the plain form resets every defaulted field the body leaves out (a PATCH of a
  first name made the person active, teamless and started today). A test (`patch-only-sent.test.ts`) fails if any
  route uses `.partial().parse(` or `.partial().safeParse(`.
- A field's own "missing" message: `z.string(missing('Paste the link'))` (zod 3's `required_error`). A whole-schema
  message: `z.enum(LIST, { error: 'Pick a topic' })` (zod 3's `errorMap`). `invalid_type_error` →
  `error: (issue) => …`.
- `.default(x)` no longer runs the schema on `x` (no transform, no check): give the final value.
- `z.record(value)` needs two arguments, `z.record(key, value)`; a `z.enum` key makes every key required (use
  `z.partialRecord` when they are not). `error.errors` is `error.issues`. `z.number()` refuses Infinity; `.int()`
  refuses numbers past 2^53.
- Do not import `zod/v3`: it is the old code with the old memory problem.
- Leave zod's messages alone unless the field needs its own words; `plainMessage` gives the plain default.

Tests and the clock:

- A test whose answer depends on the day calls `pinBusinessClock()` (test/helpers.ts) at the top of the file: Wed
  21 Oct 2026, 15:00 London, ticking from there. `FIXED_BUSINESS_NOW` holds that moment.
- Compare seeded or saved times with `nowISO()` / `todayISO()` (the business clock), not `new Date()` (the real
  clock): they differ under `LM_BUSINESS_NOW` and in pinned tests.
- A file time a test depends on is set with `utimesSync`, not left to when the file was written.
- A timing budget is judged on the best of several runs: the test files run side by side, and CI runners (Mac
  especially) are slower.
- Run `npm run test:dates` after changing anything with dates in it.

## 9. Tests

New:

- `server/src/test/dependency-safety.test.ts` (5): versions past the published fixes (body-parser ≥ 2.4.0, zod ≥
  4.6.6, nodemailer ≥ 10.1.4, read from what Node actually loads); a list far over its limit refused with one problem
  (failed on 1.4.0: 100,001 problems, 6,589,000 characters); at most 20 problems then "And 180 more problems"; plain
  messages, with a schema's own message still winning; compressed bodies (gzip, deflate, brotli) with extra bytes
  answered while the server stays up.
- `server/src/test/patch-only-sent.test.ts` (5): PATCH of a person, a campaign, an event and an interview keeps the
  fields it does not send (passed on zod 3, failed on plain zod 4 for all four), and no route uses
  `.partial().parse()`.

Changed (each fails on the date shown with the 1.4.0 version, passes now): recruitment-plus (2026-11-20),
statements (2027-06-01), statements-r3-minors (2028-01-09 23:30), videos-files (2027-06-01), bulk-gauges
(2028-01-01 00:00, and any run in the first minute after midnight), client-portal-seed and payments-api X-1
(`LM_BUSINESS_NOW` set), recruitment-plus-seed (fixed day for a deterministic seed), checkins (timing judged on
the best of five).

Counts: shared 542, server 853 (843 + 10 new): 1,395 in all.

Flaky and order-dependent tests: three back-to-back `npm test` runs on the final code all passed (1,395 each) in
88 s, 87 s and 83 s (1.4.0 took 95 s on the same machine). The one flaky test found was the checkins timing check,
which failed once at 234.7 ms while a typecheck ran beside the suite; it is now judged on the best of five answers.
Each test file runs in its own process, so no state is shared between files; the tests inside a file run in order
on purpose (several build on the one before).

## 10. CHANGELOG bullets

### Fixed
- The tests no longer depend on the real date: they passed only before 12 Nov 2026, outside the first minute after
  midnight and while the business clock matched the computer's. `npm run test:dates` runs the suite on other days.
- A form sent with a huge list is refused at once with one short message, instead of an answer listing every item
  (up to 100,000 problems and several megabytes).
- Known security problems in body-parser, zod and nodemailer (via mailparser) are fixed; `npm audit` finds none.

### Changed
- Refused forms explain themselves in plain words ("Required", "Use at most 6 characters", "Choose one of: …") and
  list at most 20 problems.
- zod 3 → 4, mailparser 3.9.36 → 3.12.4, body-parser 2.3.0 → 2.4.0.
- CI runs every check on Linux and Mac, fails on a high or critical advisory in the app's packages, runs the tests on
  four other dates, and runs every Monday; Dependabot sends weekly grouped updates.

## 11. Not done, and why

- **ESLint** (the non-CI half of CODE-8) is not added. A linter over 132k lines would need a config agreed by
  whoever maintains the code and a pass over files every other 1.5 package is editing; it belongs in its own change
  after 1.5 is merged. TypeScript's strict typecheck runs on every change on both systems.
- **The body-parser denial of service** could not be reproduced on Node 22.22 or 20.20 (see section 5); the
  update is taken anyway, and the regression test covers the three compressed encodings.

## 12. Notes for the integrator

- **package.json / package-lock.json:** other packages change these too. Keep every package.json change (this one:
  `test:dates` in the root, zod `^4.6.7` and mailparser `3.12.4` in server), then run `npm install` to rebuild the
  lockfile rather than merging it by hand; `npm audit --omit=dev --audit-level=high` must still pass, and CI fails if
  the lockfile is out of step.
- **server/src/app.ts:** this package changed the zod import, added `import { plainMessage } from './lib/validate.ts'`,
  the `z.config(...)` line at the top of `createApp`, and the 20-problem cap in `errorHandler`. Nothing near the
  cookie, HSTS or CSP lines.
- **Route files** touched by one line each (a `parsePatch` call and its import): users, campaigns, events, gauges,
  recruitment, recruitmentPlus; learning and videos for the zod 4 message options.
- After merging, run `npm run typecheck` (catches zod 3 options such as `required_error` or one-argument
  `z.record`), `npm test` (the `.partial().parse()` guard catches PATCH routes), and **`npm run test:dates`**: the
  other packages' new tests write `new Date()` times next to business-clock values in places, and the business-clock-
  only run shows whether any of those depend on the two clocks agreeing.
