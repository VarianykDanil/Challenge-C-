# 1.5 — keys: the app key, backups, restore, updates and system health

Package **keys** (branch `fix9-keys`). Findings fixed: REL-1, SEC-7, SECURITY-MISSED-3, REL-3 (backups part), REL-4,
REL-5, REL-7, RELIABILITY-MISSED-2, RELIABILITY-MISSED-3, RELIABILITY-MISSED-4, CODE-MISSED-4, REL-9, REL-10, SEC-8.

The aim: the app key and the backups can no longer be lost quietly, and problems reach the people who can fix them.

## 1. What changed, in one screen

| Area | Before (1.4.0) | Now |
| --- | --- | --- |
| App key missing at start | A new key was made silently; bank details, two-step secrets and PINs became unreadable for good | The server **refuses to start** (exit code 78) with the recovery steps; a new key is made only for a database with nothing locked yet |
| Wrong app key | Started anyway; decrypt errors later | Refuses to start; says which key fingerprint the database needs |
| Key copy in the backups folder | Overwritten by any new key | Never overwritten; a different key is saved beside it as `app-secret-<fingerprint>` |
| Key on paper | Nothing | **Recovery sheet**, made and confirmed only on the server computer (`npm run recovery-sheet`): the key never travels over the network and no API returns it |
| Key in local backups | Always (with the always-on service) | Until the owner confirms the sheet by typing the **whole key** back from the paper, then left out |
| `service:install` with `LM_APP_SECRET` | Refused to carry it | Hands it over in a private file outside the data folder |
| `service:install` run again (by hand or by `npm run latest`) | Rebuilt from the terminal only | Keeps every setting of the installed service the terminal leaves unset, and its key file; says what it kept (`--fresh` to start clean) |
| Commands from a plain terminal (doctor, backup, restore, key:restore, recovery-sheet) | Terminal settings only | Without their own `DB_PATH`, they use the installed service's database, folders and key |
| Uploaded files (statement PDFs, signature image) | Not in any backup | In every backup (`linear-….files/`), and put back by restore |
| Off-site copies | A manual weekly chore | Automatic, **encrypted** `.lhbk` copy after every backup when `LM_OFFSITE_DIR` is set; restore reads it |
| Restore over newer payments | Silently forgot them | Lists them; needs **RESTORE** typed; leaves a warning in the app. If the comparison cannot be made, it says so and still needs RESTORE |
| `npm run latest` | No backup; service kept serving during `npm ci` | Stops the service, makes and checks a backup of the service's own database first, starts the service again with its settings |
| Schema upgrade | Step by step | One transaction: all or nothing |
| Database connection | No busy timeout; `synchronous=NORMAL`; nested `transaction()` unsafe | 5 s busy timeout; `synchronous=FULL`; nesting uses savepoints |
| Problems | Seen only by someone who looked | Needs-attention bell (kind **System health**, plain words, no commands), `logs/errors.log`, `npm run doctor` |
| Node version | `>=22.18`, experimental warning hidden | Pinned to tested LTS lines; doctor shows the Node and node:sqlite status |

## 2. The app key (REL-1)

**Fingerprint.** The database now records the key's fingerprint in `meta.app_key_fingerprint` (HMAC-SHA256 of a fixed
label under the key: it identifies the key but cannot be turned back into it). It is shown as `3F2A-91BC-07DE`.

**Start-up check** (`server/src/lib/appKey.ts`, called by `index.ts` before anything reads or makes a key):

- The database "holds locked data" when any of these exist: two-step secrets, peppered PINs, bank details, payment
  connection secrets, approved payees, bank files, the Gmail password.
- Key missing + locked data → refuse to start.
- Key missing + nothing locked → make a new key and record its fingerprint (a brand-new install).
- Key present, fingerprint recorded and different + locked data → refuse to start.
- Key present, no fingerprint yet (a 1.4.0 database) → try the key on a few locked values; if it opens them (or they
  were written under the old development key), record its fingerprint; if it opens none, refuse.
- After the check, making a new key is switched off for the rest of the process (`setKeyCreation(false)`).

The refusal message names the database, what is locked, the fingerprint it needs, and three ways back:
`npm run key:restore` (type the key from the sheet), `npm run key:restore -- --from <file>.lhbk` (off-site copy),
`npm run key:restore -- --file <backups>/app-secret`. Exit code 78; the systemd user unit written by
`npm run service:install` has `RestartPreventExitStatus=78`, so it does not restart in a loop (launchd retries every
10 s; the log shows the message).

**`npm run key:restore`** (new). Reads the key typed (or piped), from `--file`, or from an off-site copy with `--from`
(passphrase from `LM_BACKUP_PASSPHRASE_FILE` or typed). It checks the key against the database first; a wrong key
changes nothing. An existing key file with a different key is kept as `app-secret.replaced-<time>`, never deleted.
The sheet prints a 64-character key in groups of four; spaces and dashes are ignored when typed back.

**Backups never overwrite a key copy.** `backups/app-secret` holding a different key is kept; the key in use is
saved beside it as `app-secret-<first 12 of fingerprint>` (mode 600), and `npm run backup` says so.

**Doctor** reports a missing or wrong key as a failure (✖) with the same recovery steps, and warns when no recovery
sheet is confirmed for the key in use.

**The seed uses the server's key.** `DB_PATH=<elsewhere> npm run seed` used to lock the demo company's bank details with
the default `server/data/app-secret`, while the server reads the key next to `DB_PATH` (or `LM_APP_SECRET_FILE`). The new
database then refused to start (1.4.0 quietly made a new key instead, and those bank details were lost). The seed now
uses the same key file as the server, and makes it there when there is none. The default location is unchanged.

## 3. The recovery sheet (SEC-7, SECURITY-MISSED-3)

One printed page: the app key, its fingerprint, where the server reads it, the database and backups folders, the
off-site folder, the recovery steps, and a warning to lock it away. **The off-site backup passphrase is never on the
sheet** (keep it on a separate paper, elsewhere: sheet + off-site access must not be enough on their own).

**Made and confirmed only on the server computer.** The codebase rule is that secrets are never returned by the API,
and the app key unlocks every other secret, so no route hands it out or takes it (a first version had the owner make
the sheet in Settings with a two-step code; a review found that against the rule, and it was removed before release).
With `npm run recovery-sheet`:

- `npm run recovery-sheet` shows the sheet in the terminal, to print or copy onto paper by hand.
- `-- --print` sends it straight to the computer's printer (`lp`, on macOS and most Linux), not to the screen. If no
  printer takes it, nothing is recorded and it says what to do instead.
- `-- --out <file>` also saves it as a text file (mode 600) to print; then delete the file and empty the Bin.
- `-- --confirm`, once it is on paper: asks for the **whole key**, typed back from the paper (case, spaces and dashes do
  not matter). This step never shows the key, so the check is against the paper, not the screen. One wrong character
  anywhere and nothing is confirmed: the backups folder keeps its copy of the key. The key is never taken on the
  command line (`--confirm=<…>` is refused: it would stay in the shell history).
- The key is checked against the database first (a wrong key is never put on paper).
- The audit trail records "Made the recovery sheet from the server command (key 3F2A-91BC-07DE). The key itself is
  never recorded" and the confirmation. Never the key.

**Settings › Backups** shows whether the sheet is done ("Printed and kept", with the date) and, until then, the three
steps in plain words: Noryn makes it with the owner on the server computer; the owner prints it and locks it away; the
owner types the key back in once from the paper. The bell item says the same ("Ask Noryn to make the recovery sheet
with you on the server computer"); other administrators are told to ask the owner. Neither offers a button.

**Key separation.** Until the owner confirms a sheet *for the key in use*, every backup keeps a copy of the key (so
nothing can become unreadable). After confirmation, backups leave it out and remove the copy of that key from the
backups folder; copies of other keys are kept (older backups may need them). A new key needs a new sheet.

**Always-on install with `LM_APP_SECRET`.** `npm run service:install` no longer refuses it:
- Linux: writes `~/.config/linear-hub/linear-hub.env` (mode 600, folder 700) with `LM_APP_SECRET=…`, and the unit gets
  `EnvironmentFile=` pointing at it. Values with spaces, quotes, `$` or `%` are refused with advice to use
  `LM_APP_SECRET_FILE`.
- macOS: writes `~/Library/Application Support/LinearHub/app-secret` (mode 600) and the LaunchAgent gets
  `LM_APP_SECRET_FILE` pointing at it, plus `LM_UPLOADS_DIR` pinned to where the uploads are now (by default they sit
  next to the key file).
- The secret is never in the unit or the plist (both are readable by others), never printed by `--print`.
- A different file already there is kept as `<file>.replaced-<time>`.
- `LM_APP_SECRET_FILE` outside the data folder already worked; install now warns when that file is missing or readable
  by others.

**Running `service:install` again keeps the service's settings.** `npm run latest` restarts the service with
`npm run service:install`, usually from a plain terminal, and people run it by hand after a Node switch. Every Linear
Hub setting the terminal leaves unset is now taken from the installed unit or LaunchAgent (a setting typed in the
terminal wins), the unit's `EnvironmentFile=` is kept, and the private key file from an earlier install is used again
when nothing else names a key. Install prints what it kept: "Kept from the service installed before (this terminal
does not set them): PORT, DB_PATH, LM_OFFSITE_DIR, LM_BACKUP_PASSPHRASE_FILE, the app key file (…)".
`npm run service:install -- --fresh` uses only the terminal's settings (to drop one) and warns when a kept key file is
left out.

**Commands from a plain terminal.** `npm run doctor`, `backup`, `restore`, `key:restore` and `recovery-sheet` used to
read only the terminal's settings, so with the key handed to the service, doctor reported it missing and the sheet could
not be made. When the terminal sets no `DB_PATH` of its own, they now take the installed service's settings for
anything left unset, and the key from its private environment file, and say so in one line. A terminal with its own
`DB_PATH` is taken at its word. (This reads the *user* service written by `service:install`; a system unit on a VPS
needs its environment file loaded, see §13.)

## 4. Backups: uploaded files and off-site copies (RELIABILITY-MISSED-2, REL-3)

**Uploaded files in every local backup.** Beside `linear-2026-10-27-0200.sqlite` there is now
`linear-2026-10-27-0200.files/` with `statements/` (client statement PDFs) and `uploads/` (the signature image), and
`media/` (learning videos) when `LM_BACKUP_VIDEOS=1`. A file unchanged since the previous backup is a hard link to the
previous copy, so a nightly snapshot costs almost no disk. Rotation removes a snapshot with its database file; an
orphan snapshot (its database file deleted by hand) goes after 24 h.

**Off-site encrypted copies.** Set two things (and keep the passphrase on paper):

```
LM_OFFSITE_DIR=/path/to/a/folder/that/is/not/on/this/disk     # a mounted cloud drive, or a folder rclone copies away
LM_BACKUP_PASSPHRASE_FILE=/path/to/passphrase.txt             # mode 600; at least 12 characters
```

Make a passphrase with `npm run backup -- --new-passphrase <file>` (six groups of five letters and digits, about
150 bits; it refuses to overwrite an existing file). After every backup (nightly, start-up catch-up, `npm run backup`)
Linear Hub writes `linear-YYYY-MM-DD-HHmm.lhbk` into `LM_OFFSITE_DIR` holding the checked database backup, the
uploaded files (videos only with `LM_BACKUP_VIDEOS=1`) and the app key, encrypted:

- AES-256-GCM; key from the passphrase with scrypt (N = 2^17, r = 8, p = 1, a fresh 16-byte salt per file); the header
  (format, scrypt settings, nonce, a passphrase check) is authenticated, so it cannot be changed unnoticed.
- Written to a private `.partial` name, **read back and checked**, then renamed. Mode 600, flushed to disk.
- 30 daily + 8 weekly copies kept there too (same rule as the local backups; never anything younger than 24 h, never
  a file that is not a `linear-….lhbk`).
- The folder is **never created** by Linear Hub: a missing folder usually means the cloud drive is not mounted, and a
  copy on this disk is not off-site. That, a missing or short passphrase, or a failed write is recorded and shown (see
  §7); the local backup is still made.
- File format (for whoever writes a reader later): `"LHBKUP1\n"` · header length (uint32 BE) · header JSON ·
  ciphertext · 16-byte GCM tag; the plaintext is gzip of entries `len(uint32) · {"name","size"} · bytes`, ended by a
  zero length; names are `manifest.json`, `linear.sqlite`, `app-secret`, `files/<statements|uploads|media>/…`.

**Restoring an off-site copy:** `npm run restore -- <path>/linear-….lhbk`. The passphrase comes from
`LM_BACKUP_PASSPHRASE_FILE` or is typed. It is decrypted into a private folder next to the database, checked, and
restored like any backup: database, uploaded files and the key. A wrong passphrase or a single changed byte is refused
and nothing in the file is used.

## 5. Restore (REL-4, REL-1, RELIABILITY-MISSED-2)

Before asking, restore now also lists what Linear Hub would **forget about money** — compared by content, not by clock:

- live payments approved that the backup has not approved;
- payments to people sent to the bank or paid that the backup still has as not sent;
- bank files made;
- bank details changed (the backup has the **old** details);
- pay runs marked paid.

When there are any, it asks for **RESTORE** to be typed (`--yes` alone is not enough; without a terminal it needs
`--yes --forget-payments`). The restored database then carries `meta.restore_payment_warning`, shown to
administrators in the bell for 14 days: "Restored from an older backup: check payments with the bank".

**It fails closed.** When the comparison cannot be made (the current database cannot be read, or its tables are not
what this version expects), restore says "Linear Hub could not compare the money records in the current database with
this backup (…)", still asks for RESTORE, and stores the warning marked `unknown`, so the bell asks the office to check
every payment with the bank.

After an off-site restore the key note now says the key came from the off-site backup (it used to say the backups
folder), and a replaced key asks for a new sheet with `npm run recovery-sheet`.

The key: restore now finds the key that opens the backup — the key in use, `app-secret` or any `app-secret-<fp>` beside
the backup, or the key inside an off-site copy — and puts it in place (an existing different key file is kept as
`<key file>.before-restore-<time>`). When none fits it says Linear Hub will not start until the key is put back with
`npm run key:restore`. For a backup that cannot tell which key it needs (no fingerprint, only PIN hashes) the old
behaviour stays: compare with `app-secret`, never overwrite.

The files: the backup's `linear-….files/` snapshot is put back — missing files copied, different files replaced (the
live one kept as `<name>.before-restore-<time>`), files added after the backup left alone. A backup from before 1.5
has no snapshot and says the folders were left as they are.

## 6. Updates and the database connection (REL-5, RELIABILITY-MISSED-4, REL-7, RELIABILITY-MISSED-3, CODE-MISSED-4)

**`npm run latest`** now:
1. refuses with local edits (as before);
2. with a background service installed, takes **the service's own settings** for anything the terminal leaves unset
   (database, port, key file, folders) and says so; relative paths are read from `server/`, as the server reads them;
3. **stops the background service** when it is installed (`launchctl bootout` / `systemctl --user stop`) and waits on
   the service's port, otherwise stops the terminal copy;
4. **backs up and checks** that database (with the uploaded files): opened again, `integrity_check`, the core tables,
   the same number of people, gauges and pay runs. No good backup → no update, and the service is started again as it
   was. (No database yet: it says there was nothing to back up.);
5. pulls, installs, builds. A failure after the pull starts the service again and says it now runs the **new**
   version, with the way back;
6. prints `To go back: git checkout <previous> && npm run setup && npm run restore -- <backup>`;
7. starts: `npm run service:install` (new version, keeping the service's settings, §3) or `npm start`.

**Schema upgrades** (`createSchema`) run in one transaction. An upgrade that fails part-way leaves the database exactly
as it was; the next start tries again.

**Connection** (`server/src/db/connection.ts`): `PRAGMA busy_timeout = 5000` (a save waits for a backup or command's
short lock instead of failing with 500), `PRAGMA synchronous = FULL` (a commit is on disk before it is acknowledged:
a power cut cannot roll back acknowledged saves). `transaction()` is safe to nest: inside an open transaction it uses a
`SAVEPOINT`, so an inner block never commits or ends the outer one and an inner throw undoes only its own writes.

## 7. System health (REL-9)

**Needs-attention bell, kind `system` ("System health"), administrators only** (`server/src/lib/attention/system.ts`):

| Item | Severity |
| --- | --- |
| The last backup failed (until a later one works) | danger |
| Automatic backups are off | warning |
| No backup for 36 hours (a fresh install gets 36 hours) | warning |
| Off-site copy failing, or cannot run (no passphrase, folder missing) | danger |
| No off-site copy for 2 days | warning |
| Off-site copies switched on, none yet / off altogether ("Backups are on this computer only") | info |
| Under 1 GB free on the data disk (under 200 MB: danger) | warning / danger |
| The app key is not on a confirmed recovery sheet (the owner: ask Noryn to make it with you on the server computer; other admins: ask the owner) | warning |
| N server errors in the last 24 hours (with where the log is) | warning |
| Restored from an older backup over payments (14 days) | danger |

All link to Settings › Backups (`/settings#backups`, the card scrolls into view), the restore item to Runs to pay.
One SQL statement per call (the meta values); the admin feed's statement budget is now 13 (other roles 12).

**Plain words.** The bell and Settings are read by office administrators, so they name no commands or settings (no
`npm run …`, `LM_BACKUP=0`, `LM_OFFSITE_DIR`): they say what happened and "ask Noryn". The commands are in these docs
and in `npm run doctor`. Each off-site problem has two wordings (`offsiteIssue` in `lib/offsite.ts`): the operator's
for doctor, start-up and the backup command, and a plain one for the office. Linear Hub's own messages are shown whole;
a raw system error is cut to 160/200 characters on a word boundary with "…" (it used to be cut mid-word).

**Cheap to show.** The off-site folder and passphrase check, and the free-disk check, run at most once a minute and are
shared by the bell and `/system/status`, so a hung network or cloud drive cannot stall every page. Writing an off-site
copy always checks afresh. The server-errors item has one key (`system:errors`) with its count, so once seen it stays
seen until more errors come (the bell's seen rule compares counts).

**Error log.** Every 500, failed backup, failed off-site copy and failed background job is written to
`<data dir>/logs/errors.log` (time, what, `[METHOD /path user N]`, error and a short stack) as well as the terminal or
service log. Never the query string or the request body. Rotated at 1 MB, five old files kept (`errors.1.log` …
`errors.5.log`). The bell counts the last 24 hours, including errors already in the file when the server starts.

**Settings › Backups** gained *App key and recovery*: the sheet status and how it is made, the key fingerprint and
whether backups still hold the key, off-site copies (last copy, or the problem in plain words), server health (last
backup failure, errors in 24 h, free disk). The card's description now says "A copy of the database and the uploaded
files every night". Its older lines no longer show commands ("On the laptop run npm run backup", "start it again
without LM_BACKUP=0", "npm run restore -- <file>"): they say to ask Noryn.

Local backup files are now mode 600 (they were 644 inside a 700 folder).

**`npm run doctor`** also checks: off-site copies (problem ✖, none yet ▲, older than 2 days ▲), the last backup
failure ▲, the key against the database (§2), the recovery sheet ▲.

## 8. Node and node:sqlite (REL-10, SEC-8) — the choice

**Decision: keep Node's built-in `node:sqlite`, and pin Node to the long-term-support lines we test.**

- Why keep it: no native add-on to compile on the owner's Mac or the VPS (better-sqlite3 needs a toolchain or a
  matching prebuilt binary for every Node upgrade), the same SQLite on every machine, and the API we use is small
  (`DatabaseSync`, `prepare/run/get/all/exec`, `isTransaction`, `backup()`). Every call goes through
  `db/connection.ts` and `lib/backup.ts`, so a change in node:sqlite is a change in two files, and a move to another
  driver is a contained job.
- Why it is safe enough: Node still labels node:sqlite "experimental", so we support only Node **22 (≥ 22.18), 24 and
  26** — `engines` is `^22.18.0 || ^24.0.0 || ^26.0.0` in the root, `server/` and `shared/` package.json (and the
  lockfile's engines lines). A test keeps them equal to `NODE_ENGINES` in `server/src/lib/nodeSupport.ts`.
- What people see: the server prints one ▲ line at start-up on any other Node; `npm run doctor` shows the Node version
  against that range (older than 22.18 ✖, odd or newer ▲) and runs node:sqlite with warnings on to report its SQLite
  version and whether this Node still marks it experimental (ℹ). The npm scripts keep hiding the runtime warning from
  everyday logs.
- The background service already runs the exact Node binary it was installed with (`staleNodeWarning` after a switch).

## 11. LOGIC changes (for docs/LOGIC.md)

- **Key fingerprint** = HMAC-SHA256(SHA-256(secret), "linear-hub:key-fingerprint"), hex; short form = first 12 hex in
  groups of four, upper case. Start-up rules as §2.
- **Backups** hold: the database (checked), `linear-….files/` (statements, uploads; media with `LM_BACKUP_VIDEOS=1`),
  the key copy until a confirmed sheet for that key, and (off-site) the key inside the encrypted copy.
- **Rotation** (local and off-site): newest per day for 30 days + newest per ISO week for 8 weeks; never younger than
  24 h; newest always kept; only files matching the name pattern; a snapshot goes with its database file.
- **Restore money check** as §5; typed word `RESTORE`; fails closed (`unknown`) when the comparison cannot be made.
- **Recovery sheet confirmed** only when the whole key typed back equals the key (`keyFromPaper`: a 64-character hex
  key ignores case, spaces and dashes; any other key is compared trimmed). Only then are backups' key copies of that
  key removed.
- **Service settings:** for `service:install` and `npm run latest`, a setting set in the terminal wins, else the
  installed service's; the hand-run commands use the service's only when the terminal sets no `DB_PATH`.
- **System health thresholds:** backup stale 36 h; off-site stale 48 h; disk low < 1 GB, critical < 200 MB; errors
  counted over 24 h; restore warning shown 14 days.
- **Transactions:** `transaction()` nests with savepoints; `createSchema` is one transaction.

## 12. Wording for the user guide (Settings › Backups)

> **App key and recovery.** Linear Hub locks bank details, two-step sign-in and PINs with one key on the server. If
> that key is lost, they cannot be read again. So the key goes on a **recovery sheet**, once. Noryn makes it with the
> owner on the computer that runs Linear Hub, so the key never travels over the network. The owner prints it, locks it
> away like a bank card (not near the server), and then types the key back in once from the paper to check it. Settings
> › Backups then says "Printed and kept". Until then, the backups folder keeps a copy of the key, so nothing can be
> lost.
>
> **If Linear Hub will not start and says the app key is missing**, do not delete anything. Ask Noryn: the key is put
> back from the sheet, and Linear Hub checks it before saving it.
>
> **Off-site copies.** When Noryn has switched them on, every backup is also copied, locked with a passphrase, to a
> folder away from the server. To open one you need that passphrase, which you keep on a separate piece of paper.
>
> **System health** items in the bell tell administrators when a backup failed, the off-site copy is late or failing,
> the disk is nearly full, the key is not on paper yet, or the server had errors.

- **Before this one update, run `npm run backup`.** The update to 1.5 is run by the 1.4.0 `update.ts` (git pulls the
  new one only during the update), which makes no backup first and does not stop the service. From 1.5 on,

- Then make the sheet with Matt, at the Mac: `npm run recovery-sheet -- --print` (or show it and copy it by hand),
  Matt locks the paper away, then `npm run recovery-sheet -- --confirm` and Matt types the key from the paper.
- With the background service installed and `LM_APP_SECRET` in use, run `npm run service:install` again so the key
  moves to the private file; later rebuilds keep it.

**Making the sheet on a VPS:** over SSH, as the service user and with the service's environment file loaded,
`npm run recovery-sheet` and copy the key onto the paper by hand (16 groups of 4), then `npm run recovery-sheet --
--confirm` and type it back from the paper: a copying mistake is caught there, before backups drop their copy.

**Lost or replaced computer (with off-site copies):** install Linear Hub (DEPLOY.md), copy the newest `.lhbk` to it,
`npm run restore -- <file>.lhbk` (type the passphrase), `npm start`, check the fingerprint against the sheet.

**Without off-site copies:** restore the newest local backup you have, then `npm run key:restore` with the sheet.

- §4 environment file: add `LM_OFFSITE_DIR=/var/lib/linear-hub/offsite` and

- §7 backups off the server: Linear Hub now writes encrypted, checked `.lhbk` copies itself (database + uploaded files

- §8 updating: `sudo systemctl stop linear-hub && sudo -u linear npm run latest -- --no-start && sudo systemctl start

  those commands read user services only, and with the wrong `DB_PATH` they would look at another database.

## 14. CHANGELOG bullets (1.5.0)

**Added**
- Recovery sheet for the app key, made and confirmed on the server computer (`npm run recovery-sheet`, `--print`,
  `--confirm`); the key never travels over the network. Confirming needs the whole key typed back from the paper, and
  keeps the key out of local backups from then on. Settings › Backups shows whether it is done.
- `npm run key:restore`: put the app key back from the sheet, a key file or an off-site backup, checked first.
- Encrypted off-site copies of every backup (`LM_OFFSITE_DIR`, `LM_BACKUP_PASSPHRASE_FILE`): database, uploaded files
  and the key, AES-256-GCM, read back before they count, 30 daily + 8 weekly kept; `npm run restore` reads them.
- Uploaded files (statement PDFs, the signature image; videos with `LM_BACKUP_VIDEOS=1`) in every backup, put back by
  restore.
- System health in the Needs-attention bell for administrators; server errors logged to `logs/errors.log` (rotated).

**Changed**
- The server refuses to start when the app key is missing or does not match a database with locked data, with the
  recovery steps (it used to make a new key silently).
- `npm run latest` stops the background service, backs up and checks the database first, and starts the service again.
- Restore lists payments, bank files, bank details changes and paid runs it would forget, and asks for RESTORE.
- `npm run service:install` hands `LM_APP_SECRET` to the service in a private file instead of refusing it, and when run
  again keeps the installed service's settings and key file (`--fresh` to start clean).
- doctor, backup, restore, key:restore and recovery-sheet run from a plain terminal use the installed service's
  database and key.
- The bell and Settings speak plainly about backups and system health: no commands or setting names.
- Database: 5 s busy timeout, `synchronous=FULL`, nestable transactions, schema upgrades in one transaction.
- Node pinned to 22.18+, 24 and 26; doctor shows the Node version and node:sqlite status.

**Fixed**
- A backup could overwrite the only saved copy of an older app key.
- A save could fail with 500 while a backup or command held the database for a moment.
- A power cut could roll back the last acknowledged saves.
- Local backup files were readable by other users of the computer (now mode 600).
- `npm run seed` with `DB_PATH` set locked the data with a different key from the one the server then used.
