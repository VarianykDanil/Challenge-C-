# 1.5 — money: what changed, for the docs

This fragment carries everything the money package changed, ready to fold into README, USER_GUIDE, API, LOGIC,
CHANGELOG and the owner notes. Plain UK English; roles are Owner/admin, office, leader, rep, recruiter, client.

## CHANGELOG bullets (Added / Changed / Fixed)

### Added
- **Days to confirm** (Pay → Days to confirm, `/pay/days`, leaders and administrators). A day someone logged with
  gauges pays a base day only when they were booked on the event, checked in, or a leader (or the office) says they
  worked it. Days with none of these, and days where everything logged was 0, wait here: "Worked" or "Not worked".
  Leaders decide for their own team; their own days are for the office. The person is told in the bell too: "1 of
  your days waits for your leader". (MON-1)
- **Days off and leaving date** for office staff (Team → person, administrators). Days off are not paid; nor is any day
  after the leaving date. A leaver's last week is still paid. (MON-8)
- **Bank details you confirm or report.** Nobody confirms their own change. When an administrator types in someone's
  details, the person sees "Your bank details were changed by … on …. Confirm or report it", with "Yes, these are
  mine" and "These are not mine". Payments to those details wait until the person, or a different administrator,
  confirms them. In an office with one administrator, the card says nobody can confirm that administrator's own
  details (payments to them are skipped until a second administrator is added). (MON-3, SECURITY-MISSED-2)
- **Two people approve each payment** (Settings → Payments). On by default once two administrators use two-step, and
  then kept on: it never switches itself off when an administrator leaves. A live payment needs a second approval
  from a different administrator; nothing is sent before it. While two or more administrators use two-step, turning
  it off needs a second administrator to agree: the first asks, the others get a red item in the bell, and a different
  one agrees with their own code (or keeps it on). (MONEY-MISSED-2)
- **Check before paying** on each payment: days waiting for a leader (not in this pay), pay resting on subs no client
  statement has confirmed, and bonuses or adjustments added in the last 7 days with who added them ("You added
  this"). Runs to pay shows the same per person. (MON-1, MONEY-MISSED-2, MONEY-MISSED-3)
- **Make a 1p test file** for a bank file connection: one payment of £0.01 to your own account, in the connection's
  layout, to check your bank takes it before the first real run; then say whether the bank took it. (MON-6, CLM-2)
- **VAT on self-billed invoices.** A supplier whose VAT number the office has checked is charged VAT at 20% on the
  invoice total (rounded down to the penny); the invoice shows the total before VAT, the VAT, the total due, the
  supplier's VAT number and "The VAT shown is your output tax due to HMRC." Payments pay the total with VAT. A VAT
  number someone types in waits, with no VAT, until an administrator who is not that person (and did not type it in)
  checks it on HMRC's "Check a UK VAT number" service and confirms it with a fresh code. The office gets a bell item
  for each number waiting. Numbers must pass HMRC's check digits. (MON-7)

### Changed
- **Bank file connections start in test mode**, like every other connection. A test file cannot pay anyone: every
  line has sort code 00-00-00 and account number 00000000 instead of the person's, so even a test file uploaded by
  mistake pays nobody. Names, amounts and the layout are real, so the file can still be checked, and its name and
  every reference say TEST. A test file marks no week paid. Switching to live needs PAY FOR REAL typed. A bank file
  connection that was live before the upgrade stays live. (CLM-3, MONEY-MISSED-1)
- **An API connection (Revolut, Wise, TrueLayer) goes live only after a test-mode payment through it got an answer
  from the provider's sandbox**, made with its current details: changing the details starts the first run again.
  Settings → Payments shows the first run step by step: test, a sandbox payment, live, a small first live run.
  (MON-5, CLM-1)
- **A downloaded bank file counts as sent.** After the first download, "Cancel the rest" needs NOT UPLOADED typed and
  a fresh code, and the file becomes void (on the page and in the audit trail). "Mark as paid" with anyone left
  unticked needs NOT PAID typed and a fresh code. A second file for the same person and week within 7 days of a file
  freed without that confirmation is refused. A new file for weeks that were in an earlier downloaded file has new
  references ("LINEAR 05OCT JL 2"), so your bank's own duplicate check can tell the two apart, and the payment page
  names the earlier file. (MON-2)
- **Wise wording:** Linear Hub creates the transfers; you fund them in Wise; transfers nobody funds go back to Runs to
  pay. (CLAIMS-MISSED-3)
- **The payroll export** is a "Payroll spreadsheet (CSV) for your accountant or payroll software", not a Xero or Sage
  import file. New columns: Worker, Adjustments, VAT, Total to pay, Invoice number. Every row adds up. It can export
  the self-billed field people and the office staff apart. (MON-4, CLM-10)
- Changing someone else's bank details, and an administrator confirming any, now needs a fresh two-step code.

### Fixed
- A week's export row now adds up: corrections from earlier weeks were in the gross but in no column. (MON-4)
- Office staff were paid Monday to Friday whatever happened; days off and leavers are now handled. (MON-8)
- The pay estimate never promises a bonus under the base-or-commission rule (bonuses are added by hand); it says how
  many more subs beat the base. Now locked by a test on the demo data. (CLM-9)
- A test-mode bank file carried each person's real sort code and account number (only the reference said TEST), so
  uploading it by mistake would have paid people and a later live run would have paid them again. Test files now
  carry 00-00-00 and 00000000 on every line.
- Anyone could add 20% VAT to their own pay by typing a made-up VAT number. A number now needs HMRC's check digits and
  an administrator's confirmation (not the person's, not whoever typed it in) before any VAT is charged.
- One administrator could switch off "Two people approve each payment" alone and then pay alone, and the default went
  off by itself when the other administrator left. It is now kept on, and turning it off needs a second administrator
  while two use two-step.

## USER_GUIDE wording

### Everyone — Settings → Bank details
- "Only you and the office's administrator can see them, and only the last digits are ever shown."
- If someone else changed your bank details you see: **"Your bank details were changed by Ada Admin on Tue 20 Oct.
  Confirm or report it."** Press **Yes, these are mine** (with your authenticator code if you use two-step) or **These
  are not mine**. Until you say yes (or another administrator confirms them), nothing is paid to them. If you report
  them, nothing is paid to them until the right ones are typed in.
- When you change your own details, the office checks them with you before the next payment goes there.
- Administrators: your own changed details are confirmed by another administrator. If you are the only one, the card
  says so: payments to you are skipped until a second administrator is added (or pay yourself outside Linear Hub).

### Leaders — Pay → Days to confirm
- "A logged day pays a base day when the person was booked on the event or checked in. These days had neither (or
  nothing was logged), so they wait for you: say whether the person worked them."
- **Worked** pays the base day; **Not worked** leaves it out. You can add a short note. Your own days are confirmed by
  the office. Paid weeks are not listed. The bell shows "N days to confirm".
- Days waiting are listed in the person's pay breakdown: "…waiting for a leader to confirm… Not paid as base days
  until confirmed."

### Reps (and leaders) — a day that waits
- The bell says **"1 of your days waits for your leader"** (for a leader: "for the office"): you logged it with no
  booking or check-in, or with nothing logged, so it is not paid as a base day until your leader confirms it. Next
  time, book onto the event and check in.

### Administrators — Finance and payments
- **Runs to pay** shows "N days to confirm" and "£X on unconfirmed subs" where they apply. Nothing there stops a
  payment.
- **A payment's page** has "Check before paying": days waiting for a leader, pay resting on unconfirmed subs (in
  total), and bonuses or adjustments added in the last 7 days, with who added them ("You added this" when it was
  you).
- **Two people approve each payment** (Settings → Payments): when on, the first approval sends nothing; a different
  administrator gives the second with their own code. It is on by default once two administrators use two-step
  verification, and it stays on if one of them leaves. Every change needs your code.
  - **Ask to turn off**: while two or more administrators use two-step, one administrator cannot turn it off alone.
    Your request waits; the other administrators get a red bell item, "Ada Admin wants to turn off two approvals".
    A different administrator presses **Agree: turn it off** (with their code), or anyone presses **Keep it on**.
  - With only one administrator who uses two-step, it stays on and says so: live payments wait, and nobody can give a
    first approval that could never be completed. Add another administrator with two-step, or turn it off (that one
    administrator can then turn it off alone; the audit trail records it).
- **Bank files**: a new bank file connection starts in test mode. Its files are named `TEST-…`, every reference starts
  `TEST`, and every line has sort code 00-00-00 and account 00000000, so a test file pays nobody even if it is
  uploaded by mistake. It is for checking the layout and the amounts. Before your first real run, press **Make a 1p
  test file**: type your own account,
  your code, upload the file to your bank and approve it there, then press **The bank took it** or **The bank refused
  it**. Switch the connection to live with PAY FOR REAL. Once you download a live file, its people count as sent: to
  cancel it you type **NOT UPLOADED** and your code, and the file becomes void (never upload it afterwards). If the bank
  paid only some, untick the others in Mark as paid, type **NOT PAID** and your code. A new file for those weeks says
  under each person "Also in bank file payment #N, downloaded … and marked as not uploaded. Check your bank did not pay
  it", and its references end in 2 (3 for a third file), so the bank can tell the files apart.
- **Revolut, Wise, TrueLayer**: test the connection, pay one person in test mode through the provider's sandbox and
  wait for the answer, then switch to live, test the live keys, and make the first live run small (one person). If you
  change a connection's details while it is in test mode, make the sandbox payment again with the new details.
  Linear Hub was built from each provider's published API; nothing has run against a real account yet, so the first
  real run is a test.
- **Wise**: "Linear Hub creates the transfers; you fund them in Wise. Transfers you do not fund in time are cancelled
  by Wise and go back to Runs to pay."
- **Team → person → Days off and leaving date** (office staff): add days off (one day, or a range: weekends are
  skipped) as holiday, sick, unpaid or other; set the last working day. A paid week cannot change: add an adjustment
  on a later week instead.
- **Finance → Payroll spreadsheet**: "Payroll spreadsheet (CSV) for your accountant or payroll software: one week's
  unpaid runs. Each row adds up, with corrections and VAT in their own columns." Choose Everyone, Self-employed
  (self-billed) only, or Office staff only. It is a spreadsheet to map, not a Xero or Sage import file.

### Reps and leaders — invoices and VAT
- Settings → Invoices → VAT number: "Only if you are VAT registered. The office checks it with HMRC before VAT at 20%
  is added to your invoices and paid with your pay." Under the field: "GB 999 9999 73 is waiting for the office to
  check it with HMRC. No VAT is added to your pay until then", then "… checked by Ada Admin on …: VAT at 20% is added
  to your invoices". A number that is not a UK VAT number (wrong shape or check digits) is refused.
- Once the office confirms it, invoices you have not accepted yet are issued again with VAT for you to check. An
  invoice to a VAT-registered supplier shows Total before VAT, VAT at 20%, Total due, and "The VAT shown is your output
  tax due to HMRC." Invoices you already accepted stay as they were: tell the office if one should change.
- Taking your VAT number off stops VAT at once.

### Administrators — checking a VAT number
- The bell says **"Check Remy Rep's VAT number"**. On Team → person → Invoice details: look the number up on HMRC's
  "Check a UK VAT number" service (the link is on the card); it must show the person's name or business. Tick "HMRC
  shows … belongs to Remy", type your code and press **Confirm VAT number**. Nobody confirms their own number or a
  number they typed in for someone else: another administrator does, or the person types it in themselves.

### Pay estimate (fix for USER_GUIDE.md:923 and :978-986)
- Replace the bonus strip text ("£75 bonus: one more sale") with: "Under the base-or-commission rule there is no
  automatic bonus (bonuses are added by the office). The estimate says how many more subs beat your day rate, e.g.
  'Beat the base: 5 more subs'." The bullet "how far you are from the bonus" becomes "how many more subs beat your day
  rate".

Changed routes:
- `PUT /api/users/:id/bank-details` (someone else's): a fresh code is required; the details wait for that person or a
  different administrator. `POST /api/users/:id/bank-details/confirm`: a fresh code is required; 403 for the
  administrator who typed them in; 409 for details the person reported.
- `PATCH /api/payments/connections/:id` `{ mode: 'live', confirm: 'PAY FOR REAL' }`: allowed for bank files now (they
  start in test mode); for an API connection 409 "Make a test payment through the … sandbox first" until a test-mode
  payment through it was answered by the sandbox. `{ mode: 'test' }` works for bank files too.
- `POST /api/payments/batches/:id/approve`: with two approvals on (live payments), the first answers the draft with
  `firstApprovedAt/By`; the same administrator again → 409 "a different administrator". With two approvals on and
  fewer than two administrators using two-step, the first approval is refused (409, `approveWaitsFor` says why).
- `POST /api/payments/batches/:id/cancel` and `/mark-paid` take `{ confirm, code }` once a live bank file was
  downloaded (`NOT UPLOADED` / `NOT PAID`); 400 without them. Cancelling then makes the file void (`voidedAt`,
  `voidedByName`, `voidReason`).
- `POST /api/payments/batches`: a new skip code `recent_file` (in a downloaded file in the last 7 days that was freed
  without the confirmation).
- `GET /api/payments/batches/:id` gains `downloadedAt/ByName`, `voidedAt/ByName`, `voidReason`, `approvalsNeeded`,
  `firstApprovedAt/By/ByName`, `recentChanges[]`, `unconfirmedPence`, `unconfirmedSubs`, `daysWaiting`, each item's
  `checks`, each item's `earlierFile { batchId, downloadedAt, downloadedByName, voidedAt, copies }` (a live bank file
  only), and actions `cancelNeedsConfirmation`, `markNotPaidNeedsConfirmation`, `voidable`, `approveWaitsFor`.
- `GET /api/payments/connections` gains `testFileAt`, `testFileResult`, `firstRun { sandboxPaymentAt, livePaymentAt }`
  (`sandboxPaymentAt` counts only a sandbox payment made since the connection's details last changed).
- `GET /api/finance/payroll`: unpaid runs gain `checks { daysWaiting, unconfirmed }` for administrators.
- `GET /api/finance/payroll/export?weekStart=&runs=unpaid|all&people=all|self_billed|office[&format=csv]`: one plain
  file (columns: Name, Employee ID, Worker, Period start, Period end, Base pay, Commission, Bonus, Overrides,
  Deductions, Adjustments, Gross pay, VAT, Total to pay, Invoice number, Payment reference). `format=xero` / `sage`
  from older links give the same file. File name `linear-hub-payroll-<week>[-self-billed|-office].csv`.
- Invoices: `Invoice.vat { net, ratePercent, vat, gross, statement } | null`; `InvoiceSummary.vatAmount` when VAT is
  charged. Payments pay `total + vatAmount`. `InvoiceProfile.vat { status: 'none' | 'waiting' | 'confirmed',
  changedAt, changedByName, confirmedAt, confirmedByName }`. `InvoiceParty.vatCharged` (supplier block: VAT is charged
  on this version). `PUT /api/invoices/profile[/:userId]`: a VAT number must pass HMRC's check digits (400 otherwise);
  a new one waits for the office.
- Bank details views gain `waitingFor`, `reportedAt`, `canConfirm`, `canReport`, `changedBySomeoneElse`,
  `noOtherAdmin`.

## LOGIC changes

- **Paid base days (MON-1).** Per person and date, a logged day counts as a base day when any of that day's gauge
  rows has something logged (> 0) AND the person was on the event's roster or checked in to it that day — or a
  `pay_day_checks` row says `confirmed`. `not_worked` never pays. Days without evidence and without a decision are
  "waiting": not paid, listed in Days to confirm (unpaid weeks, last 35 days), named in the breakdown. A leader or the
  office logging gauges for someone else confirms the day (`source 'logged'`). Commission is unchanged: it follows the
  subs. Days after a leaving date are never paid.
- **Grandfathering.** The check switches on with meta `ext:pay:day_checks = 'on'`, set (once, in a transaction) by the
  upgrade of an existing database, the end of a fresh demo seed, or the first gauge write; every day already logged
  then is recorded as `confirmed` with `source 'before'`, so no existing pay changes.
- **Office staff days (MON-8).** Mon–Fri from the start date to today (and to the leaving date), less `staff_absences`
  weekdays. A leaver keeps the run of their last week even when marked as left.
- **Pay resting on unconfirmed subs (MONEY-MISSED-3).** From the stored calculation of a base-or-commission week:
  amount = paid now − max(base, commission − commission of campaigns whose subs no statement confirmed). Listed per
  run (checks.unconfirmed) and in total per payment; campaigns whose client sends no statements are named.
- **Bank details hold (MON-3).** Payments use details only when confirmed after their last change by someone other
  than the person who made it: the person's own change → an administrator (with a fresh code); an administrator's
  change → the person ("Yes, these are mine") or a different administrator. Details whose changer was deleted are
  treated as the person's own change (an administrator confirms them). Reported details are held until new ones
  are saved. The upgrade re-holds, once, 1.4.0 details an administrator typed in and "confirmed" themselves
  (meta `ext:payments:bank-rehold`, a system audit row).
- **Downloaded bank files (MON-2).** A live file counts as sent from its first download (`downloaded_at`). Freeing
  its items afterwards needs the typed words and a fresh code (`freed_confirmed_at`); a cancel makes it void. A new live
  payment for a person-week in such a file downloaded within 7 days and freed without that confirmation is skipped
  (`recent_file`) until the old one is confirmed void. The upgrade takes 1.4.0 downloads from the audit trail (meta
  `ext:payments:downloads`). Each item of a new live file carries a copy number in its reference (1 + the earlier live
  downloaded files that held the same person-week and let it go): `defaultPaymentReference(week, name, copy)` →
  "LINEAR 05OCT JL 2" (at most 18 characters).
- **Two approvals (MONEY-MISSED-2).** Meta `ext:payments:two_approvals`: `on` / `off` (an administrator chose) or
  `auto-on` (the default, stored the first time it is read, or at start-up, once two or more active administrators use
  two-step; it is never switched off by a change in that count). Unset with fewer than two → off. Applies to live
  payments only. First approval: `first_approved_at/by`, status stays draft, nothing is sent; the second must be a
  different administrator; the payment's `approved_at/by` is the second (business clock). `stuck` = on with fewer
  than two such administrators: a first approval is refused (it could never be completed); one already given by
  someone else can still get its second. Turning off: with two or more such administrators, the first request is
  stored in meta `ext:payments:two_approvals_off_request` `{ by, at }` (202) and the setting stays on; a different
  administrator's PUT false turns it off; any PUT true cancels the request; with fewer than two, PUT false turns it
  off at once. Every change checks a fresh code last (a refused change keeps the code) and is audited.
- **Test mode for bank files (CLM-3).** Test files: name prefix `TEST-`, every reference `TEST …` (shared
  `testPaymentReference`), and every line written with sort code `000000` and account `00000000`
  (`buildBankFile(…, { test: true })`; the person's real details are still checked, so a line the bank would refuse
  still shows in the test). Mark as paid marks no week paid; a test file's download is recorded but does not count
  as sent.
- **Live gate for API connections (MON-5).** `firstRun.sandboxPaymentAt` = the first approved test-mode batch through
  the connection with an item the sandbox answered (a provider reference), approved at or after
  `payment_connections.details_changed_at` (set when an API connection's settings or secrets change). Switching to
  live is refused before it.
- **VAT (MON-7).** VAT = floor(net pence × 20 / 100), from the invoice's stored total and supplier block, only when
  that block has `vatCharged: true` (so it is frozen with the accepted invoice; a 1.4.0 invoice that printed a VAT
  number charges none). A supplier block prints the VAT number and sets `vatCharged` only when the person's number is
  confirmed (`users.vat_confirmed_at`). Typing a different number (person or administrator) records
  `vat_changed_at/by` and clears the confirmation; taking it off clears all four. `confirmInvoiceVat` needs an
  administrator who is not the person and not `vat_changed_by`, the number they checked (normalised, equal to the
  stored one) and a fresh code (checked last). VAT starting (confirmed) or stopping (a confirmed number changed or
  removed) reissues open invoices that do not count as accepted yet (a system audit row); accepted, deemed-accepted
  and in-payment ones keep what was accepted. An address change refreshes open invoices' supplier block but keeps
  each one's VAT. Payment amount = run gross in pence + VAT pence (`amountToPayPence`). Check digits
  (`isValidVatCheckDigits`): 8,7,6,5,4,3,2 × the first seven digits + the last two as a number ≡ 0 (mod 97), or ≡ 42
  for numbers from 100 000 000 (the 9755 scheme); all-zero numbers are refused; a branch's 3 extra digits are not
  checked.
- **A person's own waiting days (MON-1).** The payments attention provider adds, for a rep or leader, their own
  waiting days (same rule as Days to confirm) as one 'pay' item in the same statement.
- **Payroll spreadsheet (MON-4).** Base + Commission + Bonus + Overrides − Deductions + Adjustments = Gross pay; Gross
  pay + VAT = Total to pay. Worker = "Self-employed (self-billed)" for reps and leaders, "Office staff" otherwise.

## Database (upgrade notes)

All upgrades are idempotent, run in the schema transaction and are tested on a 1.4.0-shaped database.

- New tables: `pay_day_checks (user_id, date, decision, source, decided_by, decided_at, note, PK(user_id, date))`,
  `staff_absences (id, user_id, date, kind, note, created_by, created_at, UNIQUE(user_id, date))`.
- New columns: `users.leaving_date`; `users.vat_changed_at, vat_changed_by, vat_confirmed_at, vat_confirmed_by`;
  `bank_accounts.reported_at, reported_note, person_seen_at`; `payment_connections.test_file_at, test_file_by,
  test_file_result, details_changed_at`; `payment_batches.downloaded_at, downloaded_by, voided_at, voided_by,
  void_reason, first_approved_at, first_approved_by`; `payment_items.freed_confirmed_at, freed_by`.
- New meta keys: `ext:pay:day_checks`, `ext:payments:bank-rehold`, `ext:payments:downloads`,
  `ext:payments:two_approvals` (`on` / `off` / `auto-on`), `ext:payments:two_approvals_off_request`.
- One-off upgrade effects: existing gauge days are recorded as confirmed (`source 'before'`); 1.4.0 bank details an
  administrator typed in and confirmed themselves go back on hold (the person or another administrator confirms them);
  1.4.0 file downloads are read from the audit trail. A 1.4.0 bank file connection that was live stays live. A VAT
  number typed in 1.4.0 (when it had no money effect) has no confirmation, so it waits for the office and adds no VAT;
  1.4.0 invoices that printed it charge none. With two or more administrators using two-step, "two approvals" is
  stored as on at the first start.
- No secret, sort code or account number is ever stored in a new column, audited or exported: the 1p test file's
  account number is in the file only (the audit row has the last 4 digits).
